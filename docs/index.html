Linux runtime / Kubernetes CRI v1

OCI Containers,
WASI and Pod VMs.

Try workloads with the Nautilus CLI and deploy them with Kubernetes through the same CRI v1 runtime. Run OCI images directly on Linux or in a dedicated VM per Pod, and WASI commands with Wasmtime.

Install Nautilus

Run your first workload

OCI containers

Pull BusyBox from the registry, print a greeting, then remove the container and its sandbox. Nautilus caches the image for the next run.

sudo nautilus run --rm busybox:1.36 echo hello

WebAssembly commands

Place a WASI Preview 1 module exporting _start in your current directory. The wasi handler runs it in Wasmtime and the CLI displays its output.

sudo nautilus run --rm --runtime wasi "file://$PWD/hello.wasm"

Pod VMs

On a KVM node with Pod VM support enabled, run an OCI image in a dedicated Linux guest and print the guest kernel version.

sudo nautilus run --rm --runtime vm busybox:1.36 uname -r

Pod VM support

Give each Pod its own Linux guest. Containers in a Pod share the guest kernel and network, and repeated tool calls can work in the same workspace.

  • Enable Pod VMsThe experimental VM handler is opt-in on Linux KVM nodes. Set up Cloud Hypervisor, virtiofsd and the guest boot files, then use --runtime vm in the CLI or runtimeClassName: nautilus-vm in Kubernetes.
  • Kubernetes acceptance testsKubelet tests covered exec, attach, logs and port forwarding. Running guests kept their boot IDs and Pod IPs across a daemon restart.
  • Pod VM benchmarksOn supported nodes, containers reuse a read-only OCI image snapshot and keep private writable layers. In a single-node test with a pre-pulled Node.js image and 16 concurrent Pods, snapshot reuse reduced P95 time from starting a new Pod sandbox to the first successful exec from 9.90 s to 5.62 s.
